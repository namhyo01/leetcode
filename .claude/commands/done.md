사용자가 문제를 다 풀었다. `CLAUDE.md`의 코치 지침을 따른다.

## 1. 검증

1. 사용자가 작성한 `solution.cpp` 를 읽는다.
2. `make test` **와 `make check`(새니타이저)를 둘 다** 돌린다.
   `-O2` 에서는 통과하는 배열 밖 접근이 흔하다.
   실패하면 **정답을 알려주지 말고** 어떤 케이스가 왜 깨지는지만 보여주고
   스스로 고칠 기회를 준다.
3. 빌드가 깨지는 게 풀이가 아니라 하네스 배선 문제라면(예: `#ifndef TESTING` 가드가
   지워져 `main` 이 중복) 그건 그냥 고쳐주고 이유를 설명한다.

## 2. 리뷰

4. 통과하면 리뷰한다. 성능을 언급할 거면 **추측하지 말고 측정**한다.
   비교 대상 구현을 스크래치패드에 만들어 재고, **두 구현의 답이 같은지도 확인**한다.
5. 이번 문제의 유형이 무엇이었는지, 왜 그 유형인지 이제 알려준다.
   가능하면 이미 푼 문제와 대비시킨다 (예: "39는 목록이라 백트래킹, 53은 값 하나라 DP").

## 3. 저장소 기록

6. 갱신한다:
   - 문제 `README.md` 의 "내 접근" 회고 (한국어). 유형, 아이디어, 점화식/불변식,
     복잡도, 측정 결과, 다시 볼 것.
   - 루트 `README.md` 진행 표 — 유형 칸을 채우고 상태를 ⬜/❌/🟡/✅ 중 **정직하게**
   - `POOL.md` 체크박스
7. 커밋 + 푸시한다. 커밋 메시지는 한국어, 접근법과 복잡도를 요약한다.

## 4. 블로그 글 발행

저장소는 `/home/namhyo/work/blog` (Jekyll + Chirpy, `namhyo01.github.io`).
**그 저장소의 `CLAUDE.md` 를 먼저 읽고 규칙을 따른다.**

8. `_posts/YYYY-MM-DD-leetcode-<번호>-<슬러그>.md` 로 만든다.
   날짜는 **푼 날**. 파일명 날짜와 frontmatter `date` 가 어긋나면 Jekyll 이 다른 날짜로 처리한다.

   ```yaml
   ---
   title: "[LeetCode] 53. Maximum Subarray"
   date: 2026-08-22 22:00:00 +0900
   categories: ["알고리즘", "<유형>"]     # 2단계까지만 (Chirpy 제약)
   tags: ["leetcode", "<유형>", "cpp"]
   description: "한 문장. 이 글에서 건질 게 뭔지."
   ---
   ```

9. 본문 구성:
   - 문제 링크 / 난이도 / 언어
   - 지문 요약 (**한국어**. 블로그 문구는 한국어다)
   - 제약 조건, 예제
   - 접근 — 왜 그 방향인지, 막혔다면 어디서 왜
   - 코드 (사용자가 쓴 것 그대로)
   - 해설 — 복잡도, 왜 이 유형인지, **측정 결과 표**
   - 관련 문제 링크 (`/posts/<슬러그>/` 형식)

10. **푸시 전에 반드시 빌드 + 링크 검사.** 내부 링크가 깨지면 배포가 실패한다.

    ```bash
    cd /home/namhyo/work/blog && docker run --rm -v "$PWD":/site -w /site \
      -u "$(id -u):$(id -g)" -e HOME=/tmp -e BUNDLE_PATH=/tmp/vendor \
      -e BUNDLE_APP_CONFIG=/tmp/.bundle ruby:3.4 \
      sh -c 'bundle install --quiet && JEKYLL_ENV=production bundle exec jekyll build \
             && bundle exec htmlproofer _site --disable-external \
                --ignore-urls "/^http:\/\/127.0.0.1/,/^http:\/\/0.0.0.0/,/^http:\/\/localhost/"'
    ```

11. **새로 만든 글 파일만 스테이징한다.** 사용자가 다른 파일을 작업 중일 수 있으므로
    `git add -A` 를 쓰지 않는다. 커밋하고 푸시한다.

## 반드시 지킬 것

- **개인 상황을 쓰지 않는다.** 이직/구직/퇴사, 재직 상태, 회사명, 면접 현황.
  글 본문뿐 아니라 **커밋 메시지에도** 해당한다. 저장소 둘 다 Public 이고,
  강제 푸시로도 옛 커밋은 GitHub 에 남는다. 쓰기 전에 거르는 수밖에 없다.
- **파일명 slug 는 발행 후 바꾸지 않는다.** giscus 댓글이 URL 에 묶여 있어
  slug 를 바꾸면 그 글의 댓글 연결이 끊긴다. 제목은 언제든 바꿔도 된다.
- 성능 수치는 **실제로 잰 값만** 적는다. 추측한 숫자를 표에 넣지 않는다.
